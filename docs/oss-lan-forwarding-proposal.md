# OSS 服务端的局域网中转方案（待选型）

本提案已被用户纠正：客户端 SOCKS5 接口保留，由中转组件适配 OSS 协议。
当前方向见 [RustDesk OSS 协议适配](rustdesk-oss-bridge.md)，下文仅保留为历史备选，不作为实施建议。

此文件是实现提案，当前 0.1.2 EXE 尚未提供下述固定端口转发功能。

## 已确认的兼容限制

现场使用官方 OSS hbbs。官方客户端启用内置代理时选择 TCP 注册；OSS hbbs 不支持该注册方式。
现场 0.1.2 日志中，21116 上游 TCP 连接成功，业务双向均为 0 字节，约 18 秒结束并重连。
这符合客户端先等待服务端握手、OSS 服务端等待请求的流程。

参考：

- [官方同类问题及维护者答复 #13010](https://github.com/rustdesk/rustdesk/issues/13010)
- [客户端 1.4.3 的 start / start_tcp / get_relay_server](https://github.com/rustdesk/rustdesk/blob/1.4.3/src/rendezvous_mediator.rs)
- [OSS handle_tcp 对 RegisterPk 返回 NOT_SUPPORT](https://github.com/rustdesk/rustdesk-server/blob/master/src/rendezvous_server.rs)

以上客户端版本用于解释已核实的源码流程；现场客户端具体版本尚未提供。
TCP 21116 还有打洞等用途，端口开放不等于支持 TCP 注册。

## 路线一：固定 TCP/UDP 转发

保留官方客户端和 OSS 服务端。中转设备 192.168.72.58 接收 RustDesk 原生连接，
仅向 rd.2iu.net 的指定端口转发。客户端不启用内置 SOCKS5，因此保留正常 UDP 注册。

| 中转设备监听 | 固定上游 | 用途 |
| --- | --- | --- |
| UDP 192.168.72.58:21116 | rd.2iu.net:21116/UDP | ID 注册、心跳和服务端通知 |
| TCP 192.168.72.58:21116 | rd.2iu.net:21116/TCP | 信令和连接请求 |
| TCP 192.168.72.58:21117 | rd.2iu.net:21117/TCP | 中继数据 |
| TCP 192.168.72.58:21115 | rd.2iu.net:21115/TCP | NAT 类型探测 |

拟定客户端配置：

```text
内置 SOCKS5：关闭，并确认后台服务也已同步
ID 服务器：192.168.72.58:21116
中继服务器：192.168.72.58:21117（显式配置，避免使用服务端下发的公网中继地址）
Key：保留原 OSS 服务端公钥
UDP：保持启用
```

先通过 UDP 注册和 TCP 中继完成上线、远控验收；在受限网络下，验收时使用强制中继以排除直连探测干扰。
不自动更改服务器全局中继策略。API 21114 当前按用户要求不排查；后续 HTTPS API 需保留域名、SNI 和证书校验，不能简单替换成未被证书覆盖的内网 IP。

实现约束：

- Go 标准库即可实现数据转发，保持无 CGo、无数据库和 Web 管理，可按架构交叉编译。
- 首次部署来源限制为 192.168.72.98/32；每个监听端口只有一个获准上游，禁止任意目标请求。
- UDP 按客户端源 IP/端口维护独立上游会话，保留回复映射，并限制会话数量、空闲时间、报文大小和资源占用。
- TCP 保留双向转发、半关闭、并发限制和超时清理。
- 启动检查所有监听端口；输出来源拒绝、目标连接失败、UDP 会话、字节统计和关闭原因，不记录报文内容。
- 配置默认位于 EXE 同目录，继续支持 NSSM 前台托管。

认证差异：原生 RustDesk TCP/UDP 没有 SOCKS5 用户名密码握手。
此路线保留来源白名单、固定上游限制和原有 RustDesk 密钥/远控授权，不能声称保留了代理账号密码认证。
在用户确认此差异之前，不把现有认证代理替换成该模式。

验收需覆盖多 PC 会话隔离、UDP 通知回传、目标 PC 只能经中转到外网时的上线和中继远控、掉线重连。
仅测试本地 echo 或端口可达不足以证明 RustDesk 可用。

## 路线二：保留 SOCKS5，补齐服务端 TCP 注册

保持现有 SOCKS5 认证和来源/目标限制，修改自建 OSS 服务端，或采用已具备等效能力的实现。
需要实现兼容的首次握手、TCP 注册、保活、在线会话路由、通知和断线清理，
并验证 TCP 与现有 UDP 注册客户端之间的互通。这不是只跳过客户端握手或增加一个响应即可完成的修改。

本路线会扩大服务端协议改动和维护范围；修改服务端前需要明确部署源码和版本。
仅在现有 SOCKS5 中增加 UDP ASSOCIATE，不会让已选择 TCP 注册的官方客户端自动改用 UDP。

## 建议

在保持官方 OSS 和客户端、优先轻量化并考虑 4G 路由器的约束下，优先路线一。
必须保留代理账号密码认证时，选择路线二或增加客户端侧受认证的隧道组件；后者不属于当前最小服务范围。
